### Live pagination and schema rejection verification

PR #150 adds thirteen live cases using the existing private mixed-schema search fixture and legacy vector query suite, without changing shared CI fixtures. Filtered fetch follows a real next token with `limit: 1`, checks distinct matching IDs and preserves field projection. Namespace listing creates two owned namespaces, follows a real next token with `limit: 1`, checks prefix isolation and distinct names, and cleans both up even on failure.

The added cases reject metadata-only documents, incorrectly typed schema values, `$match_phrase` update/delete filters, dense-plus-sparse scoring, a field on `query_string`, and empty/whitespace text queries. They cover cross-plane rejection in both directions and unqualified query-string search; existing scoring cases now request `topK` greater than the corpus as well as `topK: 1`.

The final focused Node run passed **39/39 tests in 28.2 seconds** across document search and legacy query, including cleanup. The documents wire suite passed **36/36**, including added null-score and nested-429 checks. TypeScript no-emit, targeted ESLint and Prettier passed. Consult PR #150 for its subsequent matrix results; this local run alone is not a full-matrix claim.

### Semantic text is a records-plane capability today

A fresh live probe on 2026-09-09 created an integrated-inference index with `multilingual-e5-large`. Create-for-model and describe returned `schema.fields.chunk_text` with `type: semantic_text`, dimension 1024, cosine metric, and separate passage/query model parameters. A subsequent `upsertDocuments` failed with `PineconeBadRequestError`: “This index is not served by the documents API.” The response directs integrated-inference writes/searches to the records routes. The generated `SemanticTextField` is response-only; normal create-index does not accept it.

The temporary index was deleted and a final describe returned not-found. [Sanitized probe evidence](https://github.com/pinecone-io/pinecone-ts-client-internal/issues/35#issuecomment-5597974915) is tracked under #35 and references #40. `src/integration/inference/integratedInference.test.ts` actively tests server-side record/query embedding, but its assertions do not constitute successful semantic-text **documents** coverage. Resolve the product/API scope explicitly before marking that #40 item complete.

## Backups, restore jobs and collections (#21, #117)

`src/control/backups/__tests__/backups.test.ts`, `src/control/collections/__tests__/collections.test.ts`, and `src/control/restoreJobs/__tests__/restoreJobs.test.ts` now contain 92 passing cases across all 12 public methods. They cover guards, default create options, generated parameter names, list dispatch (including keeping `includeDeleted` out of project lists), and restore request payloads with OnDemand and Dedicated read capacity. The “zero coverage at any level” title of #21 is stale.

`src/integration/control/backups.test.ts` runs backup create/list-by-index/list-project/describe/delete, asynchronous restore acceptance, restore-job describe/list, and unknown-backup errors by default. It follows pagination and owns both indexes and its backup. The opt-in full lifecycle ages records for the documented 15-minute backup eligibility window, waits for completion, checks read capacity and restored count/vector/metadata contents, and cleans up. PR #136 records a successful full local Node run (17m39s); that is not evidence for every matrix leg.

Still open:

- **#117:** Run the full restore lifecycle on every required release matrix leg. A deterministic still-pending backup rejection case also needs a controllable fixture; observing pending immediately before restore cannot prevent a completion race.
- **#21:** Provision a dedicated stable pod source and execute the existing collection create/list/describe/delete test. The suite only reads/snapshots this source. The 2026-07 create API cannot provision pod deployments, so a normal ephemeral managed fixture does not satisfy this criterion.

See `src/integration/control/README.md` for the gates, commands and timeout budget. Do not close either ticket solely because default CI is green.

## Corrections to historical #40 expectations

The original mocked-wire 429 “retry-then-wrap” expectation does not describe current SDK behavior: `src/utils/fetch.ts` retries HTTP 5xx only. PR #150 explicitly verifies that all six document operations preserve a nested 429 message, make one attempt even with a retry budget, and raise `PineconeUnmappedHttpError`. Changing the retry policy or adding a dedicated 429 error class would be a runtime/product change, not completion of a missing test. Null-score deserialization is now covered separately.

The explicit live schema enforcement, scoring negatives, pagination, and cross-plane cases identified by the original plan are now implemented in PR #150 and passed locally as listed above. Remaining unavailable/opt-in scenarios stay open. The optional fixture consolidation suggested by #40 is incomplete: mixed-schema search remains a private per-suite fixture and dense/sparse update fixtures remain separate. Their provisioning cost has not been amortized across the entire matrix; that is an optimization rather than an absent assertion.

## Release decision

Prioritize the remaining fleet behavior (#35/#17), product scope for semantic-text documents, required fixture/full-lifecycle execution (#21/#117/#38). Keyless coverage now protects the document envelopes, wire contract, namespace scoping, retry behavior and error paths that the old #40 matrix called absent. Green default CI is a useful gate, but it is not completion of every original #40 scenario or of the opt-in and unavailable scenarios above.
